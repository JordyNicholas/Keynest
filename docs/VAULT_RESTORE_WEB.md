# Native encrypted-file restore workflow

Implemented through maintainer-approved [#245](https://github.com/JordyNicholas/Keynest/pull/245) for #244 / #154, building on the authenticated API accepted and merged through #241 / [ADR-0015](ADR-0015-authenticated-native-restore.md). Duplicate/conflict resolution is accepted and merged through [#249](https://github.com/JordyNicholas/Keynest/pull/249) / [ADR-0016](ADR-0016-restore-conflict-resolution.md). The [November 23 Chrome/Ubuntu rehearsal](MVP_RELEASE_EVIDENCE.md#november-23-maintainer-verification--native-restore-and-core-release-paths) records actual results and limits; Windows/Edge and unreported human scenarios remain unverified.

## Using a `.keynest` file

1. Run matching Keynest API and web builds containing #249. Sign in to the account that should receive the items, on this instance or another compatible Keynest instance.
2. Open **Vault → Restore** and choose the exported `.keynest` file.
3. Enter the **backup passphrase chosen during export** and select **Review encrypted file**. Review does not write items.
4. Review the add/update/ignore counts. Identical entries and changed matches default to **Ignore**. For changed matches, choose **Update existing**, **Ignore** or **Keep both**; choose the receiving target when several match. Keep both deliberately adds another item. Changing choices requires **Review selected actions** again.
5. For a plan with writes, enter the **receiving account’s current password**. If updating entries, also acknowledge replacement before selecting **Verify and restore items**. An all-ignored review requires no account password or apply and writes nothing.
6. On confirmed success, check the refreshed Vault. Current filters still apply. Verify a restored item before relying on the backup. If the outcome is uncertain, close and refresh before attempting another restore.

The file is an authenticated encrypted container holding Keynest’s versioned native JSON. It does not need the source instance’s encryption key or original account password. The backup passphrase cannot be reset. Restore preserves the receiving account policy and does not implicitly replace existing items. Repeated identical entries default to Ignore; Keep both intentionally adds duplicates, while acknowledged Update existing replaces only the selected entries. Store the passphrase separately from the file. Other password managers require their own migration formats; `.keynest` is the native Keynest restore path. Retained-key database backups remain necessary for complete instance/account recovery.

## Workflow and privacy contract

Enter Restore from the signed-in Vault. Opening it conceals revealed passwords; export and restore dialogs cannot overlap. Select an encrypted `.keynest` file and enter its backup passphrase. The browser checks bounded v1 framing before uploading, reads one file at a time, and sends canonical Base64 only to the configured authenticated API. Ordinary/plaintext files and oversized files are refused locally; cryptographic authentication, schema validation, owner binding and resource limits remain server decisions. No filename is sent.

Review writes nothing. The conflict-resolution refinement in [ADR-0016](ADR-0016-restore-conflict-resolution.md) shows incoming entries, candidate destination labels/dates, changed-field names and add/update/ignore counts. Password values stay hidden. Identical entries and changed matches default to Ignore. Choose Update existing with an explicit target, Ignore, or Keep both; changing a choice invalidates confirmation and requires Review selected actions again. An already-identical target is up to date; Keep both explicitly adds another item. Creation/update bookkeeping timestamps do not cause false login differences. The receiving account policy remains unchanged.

Apply requires the current account password and explicit replacement acknowledgment when updates are selected. It uses only immutable actions/targets stored in the new server review, with account/session/credential/file/receiving-state binding. New items get fresh identities and preserve history. Updates keep the existing identity/creation date, copy incoming login/expiry/reminder/rotation/policy values, reseal under the receiving key and mark updated now. Ignore writes nothing; an all-ignored UI requests no password/apply. Credentials/acknowledgment clear immediately on submit or choice changes. The selected File is reread and independently authenticated. All selected writes commit or roll back together, without automatic retry. Confirmed success refreshes the same account and announces additions/updates/ignores; current filters still apply. Late cross-session results cannot refresh another account.

The backup passphrase stays masked between preview and apply for at most the review lifetime. File handles, credentials, owned read buffers, pending readers/HTTP subscriptions, owner-visible review metadata, decision/target IDs and plan references clear on expiry, close, hiding, session change and destruction. A different file clears credentials/review; editing its passphrase invalidates review and clears the account credential while retaining the file. No file, review/decision state or credentials are added to browser storage, URL/history, logs, telemetry or AI context. JavaScript/browser/HTTP copies cannot be reliably erased; the original file remains on the user's device. Existing session storage is unchanged.

Unknown apply outcomes (including lost connections, unrecognized responses, or a generic transaction failure that may conceal a lost commit acknowledgement) clear the payload and block further submissions in that dialog. A persistent message requires closing and refreshing the Vault before another restore. Tab hiding after apply was sent follows the same rule. Closing/unsubscribing cannot retract bytes or undo a server commit. Explicit fixed refusal codes invalidate the review; retry requires a new user-initiated review. Consumed/expired/restarted or differently routed plans fail closed under ADR-0015's process-local limits. Expiry cancels idle previews; a sent apply is not interrupted just because the plan's review deadline passes.

Native backups do not replace separately retained database/key backups, provide account recovery or imply third-party importer compatibility. This UI adds no crypto, schema, key, session transport, agent capability or runtime dependency. Rollback removes the dialog/entry point and restores prior export copy; already restored rows remain ordinary Vault items.

## Verification

Component/HTTP tests cover framing and size refusal before upload, canonical encoding across chunk boundaries, exact preview/apply requests, no writes during review, immediate credential/read-buffer cleanup, no extra storage, no double submission, edits/expiry, abort/close/page-hide handling, fixed refusals, uncertain outcomes, malformed responses, session changes and unauthorized responses. Vault tests cover concealment, dialog exclusion and confirmed-success refresh for the same account. Retain the real PostgreSQL cross-database/key/restart tests and packaged/hosted API export-to-restore smoke from #241.

The November 23 maintainer report verifies the Chrome/Ubuntu browser checklist, duplicate Ignore counts, cancel/tab-hide cleanup and a pre-acceptance connection abort; see the linked record for exact scope. Windows/Edge, explicit conflict choices, cross-instance native browser-file round trips and post-commit lost-response behavior are not separately claimed by that report. Before claiming those scenarios, use disposable records to download a real file, select it in a different account/instance, preview/apply and reveal the preserved password on the claimed platform. Verify keyboard/focus return, narrow layouts, reduced motion, wrong phrases, session expiry, cancel and lost-response behavior, duplicate disclosure and current-filter messaging. Record exact SHAs, browser versions and actual results. Request mocks alone do not prove browser file IO or the complete human journey.
