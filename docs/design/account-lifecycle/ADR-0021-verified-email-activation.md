# ADR 0021 — Verified-email activation and existing-owner verification

## Status and scope

**Proposed, November 28, 2026; design issue [#300](https://github.com/JordyNicholas/Keynest/issues/300).** This document makes the maintainer-approved direction concrete for review. It does not implement mail, reserve configuration names, accept T01, or amend an accepted authentication contract. Numerical limits, endpoint names and the detailed journey below are recommendations awaiting review.

The approved direction is mandatory verification before **new** account activation, installation-controlled mail infrastructure, and continued password sign-in/Vault access for existing owners with a verification prompt. There is no operator switch permitting unverified new accounts. Private installations supply their own mail service too.

Recommend email-only signup, an inert mailbox link, explicit password selection/activation, then ordinary password sign-in. The final sign-in is a deliberate refinement of #300's earlier proposed automatic session: activation returns no bearer and mailbox possession is never a login method. This extra step and the existing-owner same-session confirmation need maintainer review before implementation.

## Verified starting point

Reviewed main `a9e9358af3cb49a4a58290c34c354e17a12a3c6c`:

Login uses case-insensitive lookup and the shared password-work budget.
- [AuthController](../../../apps/manager-api/src/main/java/dev/keynest/manager/auth/AuthController.java) exposes credential-based `/auth/register`; [UserAccount](../../../apps/manager-api/src/main/java/dev/keynest/manager/auth/UserAccount.java) has no verified-email state. The current identity maximum is 320 characters. These are application identifiers, not a promise that every accepted string is deliverable.
- [Password change](../../../apps/manager-api/src/main/java/dev/keynest/manager/auth/PasswordChangeTransactions.java) checks the current hash/session under the owner lock and replaces all sessions. [ADR-0018](../../architecture/decisions/ADR-0018-account-password-change.md) records the atomic boundary. [ADR-0017](../../architecture/decisions/ADR-0017-owner-wide-session-revocation.md) records revoke-all.
- [ADR-0007](../../architecture/decisions/ADR-0007-session-token-storage-and-browser-transport.md) still governs bearer/sessionStorage transport. The [cookie reassessment](../browser-transport/ADR_0007_REASSESSMENT.md) is a separate migration. No verification implementation or SMTP delivery evidence is claimed here.

## Threats and boundaries

The design addresses pre-registration with another person's email/password, existing-account claiming, registration enumeration, link theft/replay, scanner activation, mail flooding, queue exhaustion and races between resend, activation and credential/session changes. It cannot prevent a compromised inbox/browser/SMTP operator from reading a link, guarantee mail delivery, or distinguish people sharing one mailbox. Verification records control of the delivery address at a point in time; it is neither identity verification nor MFA.

The proposed activation creates **only a new account**. It never attaches a pending password to an existing owner, merges accounts, changes an existing password, recovers a Vault, or imports authority from an OIDC claim. Existing accounts retain their passwords, sessions, data and key custody. Public signup against an existing identifier sends no signup link. A mailbox owner who cannot sign into that existing account cannot use this flow to take it over; recovery remains a separate design.

## Identity and delivery-address policy

Preserve the existing trimmed, whole-address lowercase application identity comparison; do not rewrite legacy rows or create a second differently normalized login namespace. Registration, pending-intent lookup, quotas, activation and database uniqueness must use the same comparison. Enforce uniqueness transactionally, including concurrent requests; the implementation must demonstrate that database comparison agrees with the Java key for the supported new-address set.

For the first delivery adapter, propose a single ASCII mailbox with a DNS domain, validated using a maintained parser plus explicit length/control-character rules: at most 64 octets in the local part and 254 in the complete mailbox. Reject lists, display names, comments, address literals, CR/LF/control characters and unsupported internationalized addresses. Do not use a handwritten comprehensive email regex, SMTP recipient probing, provider-specific dot/plus removal, Unicode folding, or automatic account merging. This narrower **new-signup** syntax requires review and explicit UI/API documentation; it does not change legacy login acceptance. A later SMTPUTF8/IDN expansion needs collision and compatibility tests first.

Retain the validated, trimmed original mailbox spelling as delivery metadata for a pending signup and the resulting account. Continue using the existing lowercase identifier for login/uniqueness. SMTP local-part case can matter under [RFC 5321 §2.4](https://www.rfc-editor.org/rfc/rfc5321.html#section-2.4); preserving delivery spelling does not change Keynest's already case-insensitive identity policy. Do not claim two case-distinct local parts can have separate Keynest accounts.

For legacy verification, derive the recipient exclusively from the owner's stored address; never accept a replacement address from the client. Historical lowercasing cannot be undone. An undeliverable or unsupported legacy address keeps access and receives an explanation that verification is unavailable; it is not silently corrected or marked verified. Email change and recovery need their own reviewed authority/notification flow.

## Proposed journeys and API

All paths below are under `/api/v1`. New routes must join the central default-deny route inventory, request bounds, no-store/error handling and existing origin policy. Exact route names are proposed; there must be only one effective signup path.

| Operation | Proposed contract and result |
| --- | --- |
| Request/resend signup | Public `POST /auth/registrations/request`, strict JSON `{email}`. A syntactically admitted request returns `202` with the same fixed body: “If this address can be used, a verification link will arrive. Check your inbox or try again later.” Return no account/challenge identifier, token, existence, delivery result or recipient cooldown. Resend uses the same operation. |
| Activate new account | Public `POST /auth/registrations/activate`, strict JSON `{token, newPassword}`. Explicit user submission atomically consumes a valid signup token and creates a verified account. Return `204`, no session. Invalid/expired/replaced/used tokens, or an identifier that now belongs to an account, share one fixed `400` result without account details. |
| Read own verification state | Add an owner-only `emailVerified` boolean to the existing authenticated account response. A legacy unverified owner sees an Account settings prompt; it does not block sign-in, navigation or Vault actions. Public APIs cannot query this state. |
| Request/resend legacy verification | Authenticated `POST /account/email-verification/request`, strict JSON `{currentPassword}`. Fresh proof is required for each accepted request; recipient/owner/session come from server authority. Return generic `202` after admission, with no token or delivery result. An already verified owner need not receive mail. |
| Confirm legacy verification | Authenticated `POST /account/email-verification/confirm`, strict JSON `{token}`. Require the same still-valid initiating session and unchanged owner/address. Atomically consume the owner-purpose token and set the verification timestamp. Return `204`; do not change the password or issue a session. |

The signup dialog initially asks for email only. Opening a link shows an accessible confirmation page; the user chooses/confirms a password and submits explicitly. Use the current account-password minimum of fifteen Unicode code points, no password normalization/trimming, and the reviewed password-change field/body ceilings (32768 UTF-16 units per password, 400 KiB JSON). Browser confirmation is not sent to the server. Tokens are exactly 43 base64url characters; reject malformed/oversized values before digest lookup. Email-only and token-only bodies have a proposed 4 KiB ceiling. Refuse unknown/duplicate fields, extra documents, query credentials, non-JSON input and oversized bodies (including unknown/chunked lengths) before expensive work.

After activation show success and ordinary sign-in, with no automatic login or automatic request retry. A lost response can mean activation committed: try normal sign-in with the chosen password; a used link cannot reset it. Failed password validation does not consume a token. Hashing/transaction failure cannot leave an activated account without the chosen credential. No raw password is retained pending mail delivery.

Legacy owners request mail from Account settings after current-password proof. The email instructs them to return to that initiating tab/session; a link opened in another browser/tab cannot silently transfer authority. If that session is unavailable, they sign in and request another link. Show clear instructions instead of automatically submitting or logging in. A password change, logout, revoke-all or session expiry invalidates the session-bound confirmation. This deliberately follows current tab-scoped bearer transport; a future cookie migration must retest its own cross-tab behavior.

For new public requests, syntax errors may return fixed `400`; client/global admission `429` and installation-wide unavailable/full-queue `503` must be decided without consulting account existence or recipient suppression. Recipient suppression still returns the same `202`, without recipient-specific Retry-After. Queue admission does not synchronously inspect account existence or contact SMTP; the worker does that later. This reduces a direct timing oracle but is not a constant-time/network anonymity guarantee. Compare admitted known/unknown responses and distributions in tests; don't claim closure of all T01 concerns from equal response text.

## Token, browser and transaction contracts

Generate 32 CSPRNG bytes and base64url-encode without padding. Persist only a SHA-256 digest plus random challenge ID, explicit purpose (`NEW_ACCOUNT` or `EXISTING_OWNER`), canonical identity, delivery-address reference, generation, timestamps and consumption state. Existing-owner records additionally bind owner ID and initiating session digest. Verify purpose and every binding as well as token digest; session, restore-ticket and future action-code tokens are not interchangeable. These are lookup digests of high-entropy random tokens, not password hashes or a new encryption scheme.

Use an operator-fixed, validated HTTPS Web origin and fixed `/verify-email` route, with the raw token only in the URL fragment. A nonsecret purpose hint in the fragment may select the appropriate form; it grants no authority and the server independently validates purpose. Never derive a link from Host, forwarded headers, a client return URL or the submitted email domain. Local mail fixtures have explicitly isolated test origins, with no production HTTP fallback. Web bootstrap reads the fragment into short-lived memory and immediately removes it with `history.replaceState`. Never place it in local/session storage, router query parameters, analytics, error reports, console output or API responses. Redact bodies at application and ingress/APM boundaries; no third-party scripts, analytics, resources or link-tracking redirects on the confirmation page. Preserve restrictive CSP, `Referrer-Policy: no-referrer` and no-store responses.

GET/HEAD, link previews and scanners only load the page. They never inspect/consume a challenge through a mutating call, activate, mark verified or create a session. Do not auto-submit from page load or fragment parsing. Submit the token only in the bounded JSON POST to the fixed intended API. URL fragments reduce server/referrer disclosure; browser history before replacement, extensions, inbox retention and malicious scripts remain risks. The link is a secret and must not appear in screenshots or support artifacts.

Propose a ten-minute token lifetime from digest commitment, enforced at consumption with server time independently of cleanup. Resend accepts at most one live generation per canonical recipient **and purpose**, with shared recipient admission quotas. A public signup request cannot invalidate an existing-owner challenge. An **admitted same-purpose** replacement invalidates its previous token/queued intent; a rejected/suppressed request must not change expiry, generation, cooldown or availability. Shared quota exhaustion can still delay an owner's next request, and unsolicited signup against an unused address can cause bounded nuisance/denial; limits reduce rather than eliminate this.

For new activation, perform bounded token lookup/admission and Argon2 work outside database locks. Then in one short transaction lock/refresh the current recipient challenge, recheck purpose/generation/expiry/unused state and account absence, create the verified account with the already computed hash, and consume the challenge. Database uniqueness is the final race guard. Failure rolls back both changes. Racing activations cannot create two accounts; a late signup token cannot attach to an existing account even if another path created it first.

For legacy requests, verify current password under the shared work budget outside the owner lock; inside a short owner-first transaction refresh/recheck the verified hash and initiating session before accepting an intent. For confirmation take the same owner lock first, then challenge lock, recheck the acting session, owner, recipient, generation, purpose and expiry, and update verification/consume together. Revoke-all, password change, logout and new writers must use compatible owner-first ordering; the existing standalone session deletion is not sufficient coordination for this new contract. Revocation ordered before confirmation denies it; confirmation ordered before revocation may succeed. Recheck expiry immediately before mutation without claiming that an in-flight transaction can cancel earlier completed work. SMTP never runs while these locks are held. Bound lock/transaction time and test deadlock/commit failure paths with real PostgreSQL.

## Delivery, retries, resource limits and retention

Add a Manager application port for verification delivery and an operator-configured SMTP adapter. Do not add network dependencies to the reusable libraries or reuse expiry-reminder delivery/outbox payloads. A durable delivery job contains only an intent/challenge reference, generation, claim/status and times; no raw token, password, full MIME body or Vault material. The associated address is sensitive metadata, protected by database/backup access controls. No new application encryption key is implied.

Proposed processing sequence:

1. The admitted HTTP request transaction records a bounded recipient intent and reference-only job. For public signup this happens uniformly before existing-account inspection. Worker lookup suppresses signup delivery for any existing account without exposing that result to the caller.
2. A database-coordinated worker atomically claims that generation once, rejects stale/expired intents and rechecks eligibility (including initiating owner/session for legacy verification), then generates the raw token in process memory. It commits the digest, binding and expiry only if that generation is still current.
3. Submit one message to the fixed SMTP service, outside the transaction. Discard the raw token/message after the bounded attempt. A resend racing SMTP may deliver an obsolete link; its old generation cannot activate. Never reset its expiry after SMTP.
4. Do not automatically retry a claimed job after restart, timeout or an ambiguous SMTP acknowledgement: its raw token is not recoverable and delivery may already have occurred. Mark abandoned claims after a bounded lease; explicit rate-limited resend creates a new generation. A crash before sending can therefore lose one mail attempt. This is an intentional availability/privacy tradeoff, not exactly-once delivery. Unclaimed jobs may be claimed within their intent lifetime.

All limits below are **proposed defaults**, not existing controls. Implement recipient and installation limits atomically in shared database state so replicas do not multiply them. A process semaphore alone is not a global limit. SMTP timeout/thread cancellation must actually close outstanding connections; a nominal timeout annotation is insufficient.

| Resource | Proposed limit / refusal |
| --- | --- |
| Recipient admission, combined purposes | At least 60 seconds between accepted intents; at most 3 per rolling hour. Unsuccessful/suppressed requests do not extend the window. Keep counters through expiry/consumption; do not reset quota on resend. |
| Client public requests | At most 10 per minute per ingress-validated client IP, in addition to existing route admission. Define trusted proxies explicitly; never trust arbitrary forwarded IPs. Shared NAT impact remains. |
| Installation delivery | At most 100 accepted intents/hour and 1000 retained pending recipient/job slots; reject uniformly when full. Bound quota-key cardinality too, including requests never admitted. Existing limits remain until the shared design is actually implemented. |
| Delivery worker | At most 2 active SMTP attempts installation-wide using expiring database claims; connection/read/write each at most 5 seconds and whole attempt at most 15 seconds, with verified cancellation behavior. |
| Intent and token | Unclaimed job expires after 5 minutes; minted token expires after 10 minutes. Expiry is checked on every transition; cleanup is not authorization. |
| Transient data | Delete terminal/expired challenges, addresses and delivery references within 24 hours; retain only quota state needed for the rolling hour, delete within 24 hours. Apply bounded batches and capped backlog behavior. User verification timestamp/delivery address remains account metadata. Backup retention is a separate operator responsibility; deletion is not retroactive erasure from backups/mailboxes. |

Operator-configurable bounds and any higher capacity need documented cost/capacity review; never permit verification bypass, infinite queues/retention, unlimited worker concurrency or disabled deadlines. Mail submission acceptance does not establish inbox receipt or ownership; only successful confirmation does.

## Operator configuration and failure behavior

Each installation supplies a sender, SMTP host/port, authentication credentials and fixed public Web origin. Credentials come through the existing deployment secret mechanism; never return them from health/config APIs, store them in the repository or reuse a Vault key/provider key. Users cannot configure SMTP destination, envelope sender, arbitrary headers or attachments. Use a simple fixed template identifying the instance, purpose, expiry and how to ignore an unsolicited message; no Vault metadata, password, tracking or third-party images.

Require authenticated TLS submission with certificate/hostname validation, implicit TLS or required STARTTLS, minimum TLS 1.2 following [RFC 8997](https://www.rfc-editor.org/rfc/rfc8997.html). No opportunistic plaintext fallback, trust-all certificates or silent console-mail fallback. The installation SMTP operator/provider still sees the recipient and link; submission TLS is not end-to-end mail encryption. Operator setup must document sender-domain authentication/deliverability and provider retention as responsibilities, not promise inbox placement.

Missing/invalid configuration disables signup and verification requests with a uniform service-unavailable response and a sanitized operator diagnostic, while existing login/Vault remains usable. Separate mail capability readiness from core liveness/readiness so an SMTP outage does not restart the application or remove existing owners' access. Do not send a real message during ordinary startup/health checks. A configured service can later fail: queued requests keep generic responses, failures cannot activate/verify anyone, and the user can explicitly resend within limits. Configuration errors never enable direct registration.

Diagnostics are fixed outcome codes and aggregate counts/queue depth, without email addresses, canonical identifiers, session/challenge digests, raw tokens, credentials, SMTP response text or MIME bodies. Disable mail-library debug and sanitize exceptions; third-party error strings may echo recipients. Do not add high-cardinality account/IP labels or claim a durable security audit trail. The operator smoke procedure must use an explicitly selected disposable inbox and separately record receipt/click/confirmation results without secrets.

## Upgrade, compatibility and rollback

Propose nullable `email_verified_at`, a non-null `legacy_access_granted` defaulting to false, and nullable original delivery-address metadata on users, plus bounded challenge/job/quota tables. A versioned migration marks **only rows present at upgrade** as legacy-access-granted; it does not invent verification timestamps, change passwords, rewrite email identifiers, touch Vault envelopes or issue/revoke sessions. Do not reserve a migration version in this design; select it against current main at implementation.

Enforce a user-row constraint requiring `email_verified_at IS NOT NULL OR legacy_access_granted`. New accounts are inserted verified in the activation transaction; old direct registration cannot insert an unverified default row. Login/session authorization accepts verified or explicitly grandfathered accounts, and rejects malformed ineligible state. Successful legacy confirmation sets the timestamp and clears the legacy exception atomically. Owner account responses show the prompt until verification; no mandatory verification deadline or hidden Vault access gate is introduced.

Replace the old password-bearing `/auth/register` behavior deliberately: return a fixed migration error (proposed `410`) without inspecting the submitted email or issuing a session. Update OpenAPI, all first-party clients, fixtures, developer onboarding and release notes together. This is a signup-contract compatibility change requiring a version/release decision before runtime ships. Do not retain a legacy direct-signup endpoint, test-profile production bypass, admin insert path or flag that circumvents verification. Preserve ordinary login/Vault APIs; an already registered owner does not need SMTP per sign-in.

Deploy with registration paused while old/new replicas overlap; old instances cannot share public signup traffic during rollout. Apply the tested migration, deploy compatible API and Web, verify old signup refusal/new activation and existing-owner access, then enable signup delivery. Migration/DB failure is not grounds to fall back to unverified signup. Test both populated upgrades and clean installs in PostgreSQL and the supported local database path.

Do not promise binary rollback to a pre-verification build: old signup behavior, schema validation and migration checks are not a safe compatibility contract. Prefer forward-fix with mail/signup disabled and existing-owner access intact. Any rollback needs a tested compatible build retaining the eligibility constraint and disabled old registration; never automatically remove the constraint or verification data. Database restore may revive consumed challenges, queued jobs and revoked sessions. Before public traffic or delivery after restore, invalidate all pending verification challenges/jobs and revoke restored sessions through a reviewed recovery procedure; prove this with a real backup/restore rehearsal. Preserve installation-key recovery requirements and disclose any data-loss boundary of an intentional database rollback.

## Implementation sequence and required evidence

Accept the detailed design before runtime work. Then split implementation into focused reviewed PRs: versioned state/eligibility migration; bounded delivery/admission adapter; new signup and legacy verification transactions/API; browser/operator integration and release compatibility. Keep signup unavailable during incomplete rollout, with existing-owner behavior covered at every step. Do not merge a halfway path that still issues unverified new accounts. Coordinate with the cookie/CSRF work: new endpoints remain bearer-compatible today and require the full CSRF/transport review before any cookie-mode enablement.

| Boundary | Evidence required before runtime acceptance |
| --- | --- |
| Eligibility and upgrade | Clean/populated database; legacy short current passwords still authenticate; existing sessions/Vault data remain usable; no fabricated verification; new unverified inserts and old signup paths fail; failed migration does not enable a bypass. |
| Identity and enumeration | Supported syntax, casing, collisions, limits and header injection; legacy incompatible address retains access; known/unknown/suppressed public requests share responses and asynchronous behavior; every error/429/503 path is payload-free and no-store. |
| Token and authority | Random/digest-only state, expiry boundaries, replay, wrong purpose, altered address/owner/session, no account merge/recovery; session/restore/action tokens rejected; link GET/HEAD/prefetch has no mutation or session. |
| Concurrency and failure | Real PostgreSQL competing activation/resend/worker claims/uniqueness; logout/revoke-all/password change ordered against owner confirmation; stale hash/expiry, database/commit/hash failures; SMTP lost acknowledgement and crashes before/after every transition. |
| Capacity and retention | Multiple replicas cannot exceed shared recipient/global/worker budgets; bounded quota keys/jobs; suppressed requests do not prolong cooldown; floods recover after expiry without starving existing sign-in/Vault; cleanup/backlog/restart tests and no raw tokens in durable queues; public signup cannot invalidate a legacy verification challenge. |
| Browser and privacy | Same/split-origin normal/reduced-motion lifecycles; keyboard/mobile confirmation/prompt, same-session legacy instructions; form cancellation/storage clearing, lost activation response, no automatic retries; fragment removed and no token/password/address leaks to logs, telemetry, referrers or third-party requests. |
| Operator delivery and recovery | TLS downgrade/certificate/hostname/deadline failures and no-mail behavior; isolated SMTP sink for deterministic CI; separately authorized disposable real SMTP/mailbox receipt and explicit activation; retained-key database restore invalidates challenges/jobs/sessions before reopening. A mail catcher or SMTP acceptance alone is not inbox-delivery evidence. |

Record exact source, database/browser/topology and sanitized results. These are **test plans**, not passing results. No external mail is sent by default; real mailbox/provider testing needs an explicit recipient/service selection and any applicable privacy/cost approval.

Export/restore still requires current-password proof. [#302](https://github.com/JordyNicholas/Keynest/issues/302)'s approved five-minute single-use email action code is an additional, separately bound design; the ten-minute signup link does not authorize it. [#301](https://github.com/JordyNicholas/Keynest/issues/301)'s optional OIDC needs its own subject/linking/fresh-authentication contract and cannot mark an existing local account verified from matching email alone. Recovery, email change, MFA and automatic migration of account identifiers remain separate decisions. No AI, keys, envelopes or publication behavior changes here.

## Alternatives and review decisions

- **Password before inbox proof:** rejected recommendation because a victim must not activate someone else's preselected credential. No active account, stored password or session exists at request time.
- **Link automatically logs in:** not recommended; explicit account creation followed by normal sign-in keeps this link outside the session-issuance boundary, with one additional user step.
- **Raw token in a durable mail outbox:** not recommended; a reference-only queue deliberately trades automatic recovery of a lost mail attempt for lower secret retention. Durable encrypted payload/retry would need a separate key-custody design.
- **Mandatory legacy lockout or automatic legacy verification:** conflicts with the maintainer's approved preserve-access direction. Reauthentication plus same-session mailbox confirmation is the proposed upgrade flow.

Review the proposed extra sign-in, supported new-address syntax, same-session legacy confirmation, numeric limits, reference-only no-replay delivery, signup API break and rollout/rollback contract together. Approval accepts design direction; runtime evidence and approval of security-sensitive implementation PRs remain separate. [The canonical roadmap](../../contributing/project/roadmap.md#5-immediate-dedicated-agent-queue-implementation-first) retains the remaining H1/M1 gates.

## Research supporting the recommendations

Primary sources inspected November 28, 2026; engineering choices and limits above are Keynest proposals, not claims mandated by these sources:

- [OWASP email validation and verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html): consistent identity policy, mailbox proof before new-account use, limited single-use tokens and enumeration/privacy controls informed the design.
- [Sudhodanan and Paverd, USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/sudhodanan): account pre-hijacking research motivates avoiding preselected attacker credentials and automatic merging. It is not a finding that current Keynest has a demonstrated takeover.
- [RFC 5321 §2.4](https://www.rfc-editor.org/rfc/rfc5321.html#section-2.4) and [RFC 8997](https://www.rfc-editor.org/rfc/rfc8997.html) inform delivery spelling and SMTP TLS policy.
- [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) distinguishes email-address confirmation from authentication and disallows email as an out-of-band authenticator. This design makes no AAL, MFA or NIST-conformance claim.
