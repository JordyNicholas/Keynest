# Keynest 0.1.1

Security dependency maintenance release of the reusable Java libraries and self-hostable Manager, under Apache-2.0. The maintainer approved the reviewed patches and conditional publication on November 24, 2026. The final tag is published only after the exact-source release gates pass; [v0.1.0](https://github.com/JordyNicholas/Keynest/releases/tag/v0.1.0) remains unchanged.

## Changes

- Spring Boot 4.0.10, aligned Jackson 2/3 dependency versions and embedded Tomcat 11.0.29 ([backend review](../security/backend-dependencies-2026-11-23.md)).
- Angular framework/compiler 21.2.26 and compatible build-tool refresh ([Web review](../security/web-dependencies-2026-11-23.md)).
- Scoped glob 14.0.6, minimatch 11.0.9 and CommonJS uuid 11.1.1 development overrides, with actual package/cache/ignore/TUF/SockJS compatibility checks ([review and maintenance criteria](../security/development-dependencies-2026-11-24.md)).
- Read-only source inventory and vulnerability workflow with pinned tools/actions, graph/coverage validation, explicit artifact scope and failure checks.
- [Broader maintenance risk review](../security/maintenance-review-2026-11-24.md) and accurate Seal v1 key-ID trust documentation. Header key IDs are not authenticated automatically; no envelope/API contract or custody change is introduced.

Core Vault, public tools, account policy, native `.keynest` backup/restore and reviewed duplicate choices remain available. AI stays optional and disabled by default. No new feature, database migration, encryption/key/session format or native-file format is introduced.

## Get the source

Use the GitHub Release source archive or check out the immutable release tag:

```bash
git clone --branch v0.1.1 --depth 1 https://github.com/JordyNicholas/Keynest.git
cd Keynest
git rev-parse HEAD
```

The GitHub Release records the exact source commit and its main-branch CI run. Compare that commit when verifying provenance. An extracted archive has no `.git` directory; use the release's recorded commit instead of running `git rev-parse` there. The historical rc.1 checkpoint remains unchanged.

Distribution remains source-based; no registry availability, prebuilt binary, signed artifact or hosted service is claimed. The final-source CI generates validated CycloneDX Java/Web inventories and an OSV report with source/input/output hashes. The release links the actual matching run and manifest checkout. Workflow artifacts retain dependency metadata for seven days; these are source inventories, not an OS/container-image SBOM, signed provenance or proof of complete safety. See [scope and reproduction](../DEPENDENCY_SECURITY.md).

## Local Manager setup

Prerequisites: Docker Engine/Desktop with Compose v2, Node.js 22 with npm, free API/PostgreSQL ports 8080/5432 and Web port 4200. The API build supplies Java 21 and Maven inside Docker. Network access to container registries, Maven Central and npm is required. Direct Java/library builds require Java 21+ and Maven 3.9+ separately.

For a **new local demonstration**, from the source root:

```bash
docker compose -p keynest-local -f deploy/docker-compose.yml up --build -d
curl --fail http://localhost:8080/actuator/health/readiness
```

Wait for HTTP 200 with `{"status":"UP"}`; the first build may take several minutes. Start Web in another terminal from the same source root:

```bash
cd apps/manager-web
npm ci
npm start
```

Open `http://localhost:4200`. This is the configured development origin; `http://127.0.0.1:4200` is a different origin and is not allowed by the default CORS configuration. The local stack contains API/PostgreSQL; Web starts separately. The local Compose credentials and vault key are public demo values: keep it local and use synthetic data. Production deployment requires separately configured non-demo credentials/key, production profile, HTTPS ingress and verified proxy/CORS settings in the [deployment guide](../DEPLOYMENT.md).

Stop local containers while retaining their database volume:

```bash
docker compose -p keynest-local -f deploy/docker-compose.yml down
```

Do not use `down --volumes` for an installation whose data you want to retain. See the [Compose runbook](../COMPOSE.md) for readiness, troubleshooting and isolated smoke tests. The demo Compose port bindings also mean simultaneous local installations need deliberate port configuration.

## Use the libraries

From the source root, with Java 21+ and Maven 3.9+:

```bash
mvn -B -pl libs/keynest-seal,libs/keynest-policy,libs/keynest-generate -am install -DskipTests
mvn -B -f examples/external-consumer/pom.xml verify
```

The standalone consumer uses version `0.1.1`, rejects Manager/Spring dependencies and prints only a fixed PASS result. Library tests run in the release CI on Java 21 and 25. See the [example](../../examples/external-consumer/README.md).

## Upgrade and recovery

Back up PostgreSQL and separately retain the exact vault key and key ID before upgrading. Stop writers and follow the [migration runbook](../DATABASE_MIGRATIONS.md); Flyway manages V1–V6 and Hibernate validates the schema. Retain the same database volume and vault key across an application update. An application-only rollback is not sufficient across an incompatible database migration; restore the matching pre-upgrade database and application version instead.

Native `.keynest` files restore supported Vault items into a signed-in receiving account using the file's backup passphrase; they do not restore account credentials, sessions or the whole installation. The backup passphrase cannot be reset. Use [Vault → Restore](../VAULT_RESTORE_WEB.md#using-a-keynest-file), review the choices and refresh before retrying an uncertain apply. Full instance recovery requires the database backup **and its matching retained vault key**. Keep file passphrases and vault keys separately from their backups; never include them in support reports.

## Limitations and deferred scope

- The API decrypts passwords server-side with one server-wide key. Metadata is plaintext in the database; the browser session bearer is JavaScript-readable. This is not zero knowledge, an independent security audit or a compliance certification.
- Rate limits and restore plans are process-local. Restore preview/apply must reach the same API process; restart or expiry requires a new review. Canceling a request cannot undo a server commit, and apply is never automatically retried.
- Windows/Edge, a separate native browser-file cross-instance round trip and lost-response-after-commit behavior are not claimed by this manual rehearsal. Automated PostgreSQL cross-database/key/restart tests provide separate evidence.
- At very narrow widths navigation can scroll horizontally; below 960px Sign out remains available on Account rather than the sidebar.
- Third-party migration destinations, public hosting, library registry publication, external reminder email, MFA, recovery keys, team RBAC/SSO, KMS, agent/MCP tools and client-side zero knowledge remain deferred. The limited Bitwarden parser/model harness does not enable a supported destination.
- BYOK policy explanation remains disabled by default and its live provider is unverified. Core functionality needs no AI key. Operational security events are payload-free, best-effort logs rather than durable attributed auditing.

Review the [threat model](../THREAT_MODEL.md), [security policy](../../SECURITY.md) and [changelog](../../CHANGELOG.md). Report vulnerabilities privately using GitHub Security Advisories; keep credentials, keys, dumps and Vault contents out of public issues.
