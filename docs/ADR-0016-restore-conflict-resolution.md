# ADR 0016 — Reviewed duplicate and conflict resolution during restore

## Status

Accepted through maintainer-approved [#249](https://github.com/JordyNicholas/Keynest/pull/249) for #248 / #154, merged as `fda972f070af68e6d957f3c0d88e29181d23307b`. The maintainer approved this interaction in chat on November 23: identical entries default to Ignore; changed matches offer Update existing, Ignore or Keep both; ambiguous targets require selection and updates require explicit confirmation. This refines the unconditional append behavior accepted in ADR-0014/0015; their file crypto, receiving-key independence, session/reauthentication and single-use boundaries remain.

## Matching and defaults

Compare only the receiving owner's Vault. Exact nonblank website and username values identify candidate logins; when either identifier is absent, label must also match exactly. This is candidate identification, not authorization or fuzzy URL/domain matching. Values are not trimmed, normalized or case folded. A match is already up to date when label, URL, username, password, historical policy ID, expiry/rotation dates and reminder lead time match. Source/current IDs and creation/update bookkeeping timestamps do not determine login equality. Date comparison uses the supported databases' microsecond storage precision; payload and insertion timestamps are unchanged.

New entries default to Add. Identical entries, changed matches and exact repeated file entries default to Ignore. Changed matches permit explicit Update existing or Keep both; an already-identical target is not a meaningful update. Keep both is an explicit Add and can intentionally create another record. Every file position receives one decision. One existing target may be updated at most once in a restore. No action deletes or automatically consolidates existing duplicates.

Review returns owner-visible source/target labels and identifiers, target creation/update dates, classification, fixed changed-field names and add/update/ignore counts. Password values and password fingerprints never appear in review. Password comparison runs server-side using the existing receiving key/AAD. Only the current candidate's opened string and the owned incoming payload are used; no persistent plaintext/hash index, secret cache or model context is introduced. JVM string copies remain best effort, as in existing reveal/export.

## Review, plan and apply

Preview may receive a complete `decisions` array of `{sourceIndex, action, targetId}`; absent decisions select safe defaults. Actions are `add`, `ignore` and `update`. Target IDs must be canonical receiving-owner candidates for that exact source position, and changed updates require a real selected target. Foreign/missing targets, repeated positions, repeated update targets, unknown fields/actions and inconsistent selections fail before writes.

The server issues a new five-minute single-use plan after reviewing the choices. It stores immutable position/action/target decisions plus the existing owner/session/credential-version binding and file/receiving-state consistency marker. It stores no labels, opened values or file. Choices cannot be supplied or changed on apply. Changing a UI selection discards its prior plan and clears account credentials/confirmation; the user must review the selected actions again.

Apply requires the existing current account-password check. Any plan containing updates additionally requires JSON `confirmUpdates: true`; the UI provides a required replacement acknowledgment. The exact file is reauthenticated and receiving state rechecked inside the transaction. A changed target/candidate set refuses the operation and requires fresh review. Marker components hash the domain/receiver/encrypted file and owner-scoped candidate metadata/ciphertext, not plaintext passwords; they are consistency markers, not authorization tokens.

Add preserves the accepted fresh-identity/history behavior. Update preserves the receiving item ID, owner and creation date, copies incoming login values/policy/expiry/rotation/reminder data, sets update time to now and reseals with the receiving key and existing item-v1 AAD for that target and incoming historical policy ID. It does not enforce today's policy on historical credentials or replace account settings. Ignore writes nothing. Counts in the committed result distinguish additions, updates and ignores. The all-ignored UI requests no account password or apply; authenticated direct API no-ops remain supported.

All writes commit or roll back together. Preview and apply lock the receiving account; normal Vault create/update/delete take the same parent lock before touching items. This serializes app writers across independent instances and prevents concurrent approvals from both applying stale decisions. Bulk work remains nonqueued, the receiving transaction has a 30-second timeout, and authorization is checked before writes and after flush. External SQL writers are outside this coordination contract. Existing expiry-reminder eligibility checks continue; notification consent/outbox is not imported.

## Bounds, privacy and compatibility

Project at most 5,001 candidate IDs before fetching ciphertext, fail above 5,000, check database-side ciphertext lengths, then fetch at most 64 bounded envelopes per batch. Review has at most 500 source entries, 5,000 source/target match references and a conservative 8 MiB JSON size budget. Overflow fails the entire review rather than silently omitting candidates. Large ambiguous sets may require a smaller export/selection.

Request parsing validates fields and streams decision objects with an immediate 500-decision limit; it does not materialize attacker-controlled nested JSON trees. Existing bounded body/file/KDF/password-work admission, no-store, fixed error/audit actions and cause-free failures remain. Review metadata, selected target IDs and decision state clear on edits, expiry, close, hide, session changes and teardown. Unknown apply results remain blocked pending a Vault refresh; unsubscribe is never described as rollback and no apply is automatically retried.

The native file/Seal/schema/key/session formats and database schema are unchanged. Public review/results add metadata and counts; preview adds optional decisions and apply adds explicit update acknowledgment. Deploy matching API and web versions together: old web clients cannot interpret partial/updated counts correctly and fail closed. Process-local plans disappear on restart; existing replica/expiry/retry limitations remain. No AI/agent capability or runtime dependency is added. Rollback removes conflict review/selection and parent-lock coordination; already committed ordinary Vault data remains readable.

## Verification

Required checks cover unchanged/repeated/within-file duplicates, changed passwords/settings, explicit target updates and Keep both, immutable identity/creation/account policy, missing/foreign/repeated targets, plan/confirmation tampering, receiving changes, bounded/streamed requests and comparison overflow before ciphertext access. Retain credential/file cleanup, transaction rollback, revocation, rate/cache/audit tests. PostgreSQL checks must run without skips for separate-key restart recovery and independent application instances actually contending on the receiving lock; the losing stale approval must refuse without a duplicate. Both Compose variants must verify repeated-file skips. Browser tests cover safe defaults, selected review, masked change flags, acknowledgment, ambiguous target selection, counts, cleanup and uncertain outcomes. [Exact merged-revision CI](https://github.com/JordyNicholas/Keynest/actions/runs/45213003321) passed. The [November 23 maintainer rehearsal](MVP_RELEASE_EVIDENCE.md#november-23-maintainer-verification--native-restore-and-core-release-paths) records Chrome/Ubuntu duplicate Ignore, Update existing, Keep both, ambiguous-target selection and lifecycle checks, with the maintainer's release GO decision. It does not claim Windows/Edge coverage or other unreported scenarios. Third-party migration under #154 is deferred; final release gates remain separate.
