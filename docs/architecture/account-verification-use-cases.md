# Account verification application use cases

Internal implementation candidate #343 under #338 and accepted [ADR-0021](decisions/ADR-0021-verified-email-activation.md), after merged [state](verification-state.md) #340 and [mail adapter](../operators/verification-mail.md) #342. This connects application transactions and an explicit one-attempt coordinator. It adds **no HTTP endpoint, Web landing flow or automatic delivery schedule**. Signup remains paused; no existing account is marked verified by migration/startup.

## New accounts

`requestSignup` requires configured mail, validates the supported mailbox and records the reference-only intent through shared admission. It does not inspect account existence or accept a password. Only the explicit dispatcher later performs worker eligibility checks, including suppressing signup mail to an existing account. Internal admission enums must not be returned verbatim by a future public adapter: recipient suppression needs the same generic 202 as admission, while independent global/client/capacity failures keep the accepted policy. Trusted client identity must come from the reviewed ingress boundary, not a client JSON field.

`activate` accepts a token and newly chosen password in caller-owned buffers. Malformed/expired/replaced/used/wrong-purpose proof cannot create an account. A non-consuming `canConsume` preflight prevents password hashing for invalid proof; it clears its supplied token copy and grants no authority. It updates only the coordination row, consumes no challenge/quota, and is neither a read-only transaction nor a public inspection API. GET/HEAD/scanners must never call it. Password validation and hashing finish **outside account transactions/locks**. New passwords require at least fifteen Unicode code points, at most 32768 UTF-16 units, nonblank content and no trimming/normalization; spaces and supplementary Unicode are tested. Caller buffers are cleared on every exit. Each application instance has one password-operation slot, in addition to the existing shared hashing budget; this is not distributed rate limiting or T01 acceptance.

The short writable READ_COMMITTED account transaction independently rechecks and consumes the current new-account generation, reparses its validated original delivery spelling, and inserts one verified owner with the precomputed password hash. Canonical database uniqueness is the final race guard. All writes roll back together on failure. A competing activation/resend/late account creation cannot merge, overwrite or reset an existing account. Activation returns no session or account metadata. Ordinary sign-in with the chosen password is required afterward, including after an uncertain response. A used link cannot change that password.

Fixed failure reasons sanitize ordinary password, persistence and commit failures without driver causes. The pinned Hibernate `org.hibernate.orm.jdbc.error` logger is off because driver constraint text can carry row values; a shared H2/PostgreSQL failed-insert test also checks that the address/generated hash does not reach captured output. Keep this default and SQL/bind tracing off; use fixed application outcomes for diagnostics. A synthetic failure after a real successful commit is tested: the result is uncertain, the owner exists, the proof is consumed, and ordinary sign-in works. This is not a claim of HTTP/network lost-response coverage before that transport exists. Password hashing failure and failed account insertion retain the unconsumed proof; there is no server-side automatic retry.

## Existing owners

`requestOwner` authenticates the current bearer and verifies the current password under the shared hashing budget before taking an owner lock. The transaction refreshes the owner, rechecks the exact verified password hash and still-active acting session, and selects the stored address itself. There is no client-supplied replacement address, owner ID or session. Already verified state is suppressed; an unsupported historical address returns unavailable-verification guidance while preserving login/Vault access. Accepted requests bind owner, original stored address and initiating session and use the same bounded shared recipient quotas.

`confirmOwner` requires that same owner/session and an owner-purpose token. It locks/refreshes the owner first, consumes the bound current proof and marks verification in the same short transaction, rechecking session expiry immediately before mutation. It preserves password/hash, sessions, password policy, Vault IDs/envelopes and installation key custody. A different valid session, another owner, a public-signup token, stale address/session, expiry, used/replaced proof or revoked session cannot confirm. Failed verification updates roll back proof consumption as well.

Logout now shares the same owner-first ordering already used by sign-in issuance, password change and revoke-all. Revocation ordered first refuses confirmation; confirmation ordered first can commit before a later revocation. Neither retroactively cancels completed work. Expired-session cleanup still removes already-expired authority; expiry is checked at use, independently of physical cleanup. Database deadlock/connection/commit failures remain fail-closed, not an invitation to retry automatically or fall back to process state. Equivalent ordering for future email-change/OIDC writers requires its own review.

## Explicit delivery coordination

`VerificationDispatcher.dispatchOne` checks configuration before claiming and refuses an enclosing account transaction. It obtains at most one committed delivery claim, passes a trusted exact-generation eligibility callback to the SMTP adapter, then records a fixed sent/failed/ambiguous result and clears the material even on failure. A thrown send is conservatively ambiguous. Stale/replaced/expired completion is terminal; there is no reclaim/replay, token renewal or automatic retry. A configuration/claim/finish failure is a fixed unavailable outcome. `EMPTY` means no delivery material was returned, including suppression/capacity; it does not certify that every queued reference is gone.

No scheduler/controller invokes this coordinator yet. This class alone does not enable mail, public signup, mailbox ownership, account recovery, export/restore action confirmation or an authentication method. The later worker must retain the database claim/lease and SMTP deadline contract. No network operation occurs inside the database transaction.

## Recovery and acceptance

A database restore can revive consumed proof and old bearer state. The explicit [operator recovery procedure](../operators/database-migrations.md#restore-authority-invalidation-v9-and-later) invalidates every pending generation/job and restored session with all writers stopped, before reopening traffic or future mail delivery. It preserves rolling quota events, existing account eligibility/credentials and Vault/key state. The SQL resource is **not a Flyway/startup task** and is not run by ordinary application construction. Its fixed lock/statement bounds fail atomically; operators keep traffic stopped on error.

The PostgreSQL dump/restore rehearsal retains the installation key, consumes a link after the backup, demonstrates that restoring the older database revives it, then runs the exact reviewed recovery SQL with all contexts closed. Restart must reject that link and restored bearer, allow ordinary password sign-in and decrypt the unchanged Vault envelope. This does not certify an operator's backup storage, recovery time, external anti-rollback ledger or actual deployment.

Shared H2/real PostgreSQL tests cover creation/no-session, proof/password bounds, preflight/hashing/transaction separation, concurrent application replicas, resend while hashing, stale proof after all three revoking writers, both confirmation/logout orders, failed writes, post-commit uncertainty, same-session authority and retained legacy credentials/Vault data. Dispatcher tests use a fake port; the earlier mail-adapter slice provides isolated TLS evidence. Real PostgreSQL, full Java/Angular/Compose and four origin/motion browser results must be recorded on the concrete PR, not inferred from H2 or a skipped container test.

Remaining #338 work includes strict bounded public DTOs/route inventory/CORS/ingress admission, generic response/timing checks, complete inert accessible Web fragment custody and activation/confirmation guidance, automatic worker rollout, real disposable-mailbox receipt/confirmation and actual deployment/recovery acceptance. Action codes #302, optional OIDC #301, cookie/CSRF migration, H1/T01/M1 and publication decisions remain separate.
