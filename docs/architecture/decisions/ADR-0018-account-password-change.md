# ADR 0018 — Account password change and session replacement

## Status

Proposed implementation decision for roadmap H4 / #308, following accepted owner-wide revocation (#309 / ADR-0017). Exact-source evidence and acceptance belong to the implementation pull request. This changes local authentication credentials, without changing session transport, encryption/key custody or recovery.

## Decision and atomic boundary

Add authenticated POST `/api/v1/auth/password`, accepting strict JSON with only `currentPassword` and `newPassword`. The bearer determines the account; no target identity is accepted. Account settings opens the existing Material confirmation pattern with current/new/confirmation fields and explicit Show/Hide. Confirmation is browser-only and is never sent. A new password must be nonblank and contain at least the same fifteen Unicode code points required by registration. Do not trim or normalize passwords, impose Vault generation rules on account authentication, or reject legacy shorter current proofs. Both credential fields are bounded to 32768 UTF-16 units and the JSON body to 400 KiB, including unknown/chunked lengths and escaped text. Duplicate/unknown fields, trailing documents, query parameters and non-JSON/non-text credentials are refused.

Verify the current password and hash the replacement with the existing Argon2id/shared password-work budget, outside the owner lock in the normal HTTP flow. A separate ten-second-timeout transaction locks and refreshes the parent account, compares the verified credential version and rechecks the acting session's ownership/expiry. Replace the hash, delete every old account session including the acting bearer, and insert a fresh session before committing. Any mutation/insert/flush/commit failure must not expose an uncommitted replacement as a successful HTTP result. The existing 256-bit CSPRNG opaque bearer, digest-only persistence and seven-day expiry are factored into one package-local issuer shared with registration/login. No new cryptographic primitive, KDF parameter or dependency is introduced.

The account lock is shared with login issuance, revoke-all and existing account-coordinated writers. An old-password login that verified before but issues after a committed change refreshes its entity and refuses the changed hash. A login ordered before change is revoked. Independent competing changes/revocations from old authority cannot both commit. An independently authorized later sign-in remains possible. Existing in-flight requests and delivered bytes cannot be retrospectively canceled; current export/restore final-check boundaries remain. Existing restore tickets are not rebound: their prior session/credential binding is refused and the owner must review again with the replacement session/current password.

## Browser and resource behavior

Clear every input immediately on submission, cancellation, hiding or destruction. Retain a single pending request with a twenty-second browser timeout, without automatic retry. On a well-formed successful response, replace the captured bearer in the existing tab-scoped session storage, stay signed in and close the dialog. Clear the old/current replacement locally if response validation or storage fails. A result from an earlier action must not overwrite or clear a different replacement account session. Existing application observers treat the new bearer as a session change and clear transient revealed data.

Definite input/password/admission failures allow explicit retry. A lost connection, timeout, unknown server failure or cancellation after submission may have committed: clear the captured local session, return home and instruct fresh sign-in with the new password first. Do not promise rollback or automatically resubmit old credentials. Normal success does not send a password or hash back to the browser. JSON/JVM/HTTP/request copies cannot be reliably erased; owned byte/char buffers are cleared best effort. No plaintext password, hash, bearer, account metadata or body enters security diagnostics. The normal existing bearer response/session storage remains intentionally accessible to JavaScript under ADR-0007.

The endpoint joins central authenticated-handler inventory, existing per-IP route admission, early no-store/body limits and a fixed payload-free `AUTH_PASSWORD_CHANGE` outcome event. One nonqueued change permit per process bounds password work; current hashing, revocation and ingress budgets remain. This is not distributed rate limiting, durable audit, a hard end-to-end deadline or immunity to targeted saturation/parent-lock contention. Driver/acquisition/network/commit behavior still needs deployment controls. Email confirmation, MFA, OIDC/provider-only proof and password recovery are separate designs and are not enabled or bypassed here.

## Data, recovery and rollback

The account password authenticates the owner. It is not the installation Vault key or native-file export passphrase. Changing it leaves all Vault envelopes, keys, metadata/policy, item passwords and earlier `.keynest` files unchanged. It does not rotate website credentials or retract copies/backups already held elsewhere. Existing native files retain their own passphrase; full recovery retains the matching installation key.

No database migration is needed. The new hash and replacement session remain compatible with the preceding application; an application rollback removes the action while the owner continues using the new password. Do not restore an older database merely to undo the UI change. A database backup taken before the change can restore an older hash and session state: password changes/revocations cannot survive arbitrary database rollback without an additional external trust mechanism. After operational recovery, verify the intended credential state and deliberately revoke/change again if needed. No mail reset or new recovery promise is implied.

## Required evidence

Unit and HTTP negatives cover current proof, new-password Unicode/length/blank boundaries, strict/oversized bodies, no-store/rate/redaction, clearing and hashing/admission failures. Real PostgreSQL verifies fresh account locks, competing changes/revoke-all/login, stale proof/session/expiry, foreign identity, transactional rollback and session-insert failure. The real retained-key PostgreSQL dump/restore rehearsal changes the password before backup and verifies the restored new credential, replacement session and unchanged readable envelope. A real restore transport test refuses the prior ticket and succeeds only after a new review. Browser tests cover valid replacement, stale/malformed results, storage failure, cancellation/visibility/timeout and no automatic replay. All four origin/motion fixtures exercise the 390px keyboard/dialog flow, old bearer/password rejection and later new-password sign-in/revocation. Source tests alone are not runtime evidence; the linked issue/PR records exact-SHA results.
