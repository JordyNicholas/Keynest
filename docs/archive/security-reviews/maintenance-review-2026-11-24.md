## Other boundaries reviewed

Workspace routes remain under both parent and child auth guards, redirecting anonymous access to the public homepage. Java controllers/services authenticate sessions and use owner-scoped access; browser guards do not grant authorization. Existing negatives cover two-user Vault CRUD/reveal/query, account policy, export/restore authorization, stale/replayed plans and reviewed conflicts. The public homepage generator/checker use transient browser values, fixed packaged policy and lifecycle cleanup; the generator uses browser cryptographic randomness rather than saving a Vault record.

Authentication responses, reveal, account-policy responses and export/restore use no-store controls in their respective paths. Session digests, revocation/expiry, owner/item/policy AAD, native backup authentication, bounded restore parsing and retained-key PostgreSQL recovery retain their existing tests. Optional AI remains off by default with authenticated, fixed-destination, allowlisted policy-only processing; no Vault/provider credential egress to a model or MCP runtime was added.

A fresh production-source search found the existing fixed-schema `SecurityEventLogger`, opt-in fixed-text console reminder adapter and Angular bootstrap-failure `console.error`. It did not find a new application payload logger, `System.out/err`, `printStackTrace`, `innerHTML`, Angular trust bypass or `eval` in the inspected paths. This does not sanitize external proxy/APM logging or establish absence of every possible injection path.

The earlier review also noted a documentation overclaim: Seal v1 does **not** authenticate its header key ID automatically. This review corrects the threat-model objective and clarifies ADR-0003. Existing Manager key selection does not derive authority from that header. No cryptographic format change is made.

## Remaining risks and release decision

The accepted architecture still has server-side opening with one server-wide key, plaintext metadata, JavaScript-readable tab bearers and XSS exposure, legacy policy-only AAD where applicable, per-process rate limits/restore plans, non-durable security events, and best-effort memory cleanup. These are not removed by dependency upgrades. The [threat register](../../security/threat-model.md#threat-register) remains authoritative; changes to custody, sessions, metadata or header authentication need separate reviewed designs and migrations.

Source dependency matching does not cover OS/base-image packages, generator/scanner toolchains, every standalone-consumer dependency, or future registry/advisory changes. No new production image scan or public-host TLS/CSP/ingress verification is claimed. CI uses mutable action tags in its established application workflow; the proposed separate dependency workflow pins its actions, but this is not release signing/provenance or comprehensive supply-chain hardening. A hosted rollout remains gated on its own image, ingress, request-size/time, proxy, CSP, secret-injection, recovery and logging verification.

At this checkpoint, no additional application exploit was independently confirmed by this scoped review. That statement is narrower than a no-risk verdict. Three identified dependency matches have a proposed fix in #263; they must not be ignored merely to publish. The maintainer's prior approval covers #260/#261, not the additional transitive-major overrides or the new security automation. Merge #263 and #257 only after their reviewed-change approvals and passing evidence, prepare the new version, then rerun exact final-source CI and inventory matching before publication. A failing or incomplete gate keeps 0.1.1 unpublished. Preserve prior tags and actual manual-test provenance.
