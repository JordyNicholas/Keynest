# Availability controls and saturation recovery

Roadmap M1 H6 / #313. **[verified]** These controls already exist in Manager API. This document records their availability trade-offs; it introduces no runtime limit, shared service or acceptance of residual risk. T01, T09 and T13 in the [threat model](../threat-model.md) remain Medium/open. Exact-source test results belong on the issue/PR, separately from the source map below.

## Admission, rejection and recovery

| Boundary | Existing control and refusal | Recovery and remaining denial risk |
| --- | --- | --- |
| Shared password work | `PasswordHashingService.withSlot` uses one nonqueued semaphore per API process. A hash/verification reaching a full budget receives generic 503. Registration, admitted known/unknown login, password tools, bulk passphrase work and current-password proofs/new account hashes share slots. | `finally` releases a slot when work exits, including provider failure. Occupying slots can deny other owners and unrelated password workflows; there is no per-owner reservation, fairness or completion-time guarantee. A disconnected caller does not prove that native work stopped. |
| Client/route windows | `RateLimitFilter.windowFor` bounds the table of resolved-client plus canonical application-relative route keys. Existing unexpired windows retain their count. When full, expired windows are pruned; a new key that still cannot fit gets 429, as does an over-budget existing key. `Retry-After` is the configured full window length, not an exact capacity forecast. | Windows expire using wall-clock time and are reclaimed on access/capacity pressure. No unexpired window is evicted to admit another client. Filling the table can deny legitimate new clients across the selected routes even when their own request count is low. Expiry does not guarantee admission while competing traffic continues. |
| Login identifiers | `LoginAttemptLimiter` separately bounds normalized-identifier entries, permits one in-flight attempt per identifier, counts verified failures and applies cooldown. A full table/in-flight conflict returns generic 429 with `Retry-After: 1`; cooldown reports rounded remaining seconds. | Monotonic-time expiry and successful sign-in release/reset eligible state; infrastructure failure releases admission without adding a credential failure. Capacity scans run at most once a second. Active entries are never evicted. An attacker can cause targeted cooldown or deny other sign-ins through table pressure/stalled work. See [full accounting and recovery semantics](login-throttling.md). |

These are decisions at particular boundaries, not universal HTTP status guarantees. Selected POST routes first pass client/route limiting; login also needs identifier admission before hashing. Input bounds, CORS, authentication and other endpoint-specific permits can reject before password work is attempted. Public/optional/authenticated route classification remains governed by the [central authentication boundary](api-authentication.md); authentication does not reserve hashing capacity. Password change releases the current-proof slot before acquiring one for the new hash, so either acquisition can fail before the mutation.

The selected client-limited POST routes are catalogued in `ApiPaths.RATE_LIMITED_POSTS`; this is not a limit on every request or every expensive operation. Export/restore also have their own process-local admission/body controls; consult ADRs [0013](../../architecture/decisions/ADR-0013-authenticated-vault-export.md), [0015](../../architecture/decisions/ADR-0015-authenticated-native-restore.md) and [0016](../../architecture/decisions/ADR-0016-restore-conflict-resolution.md) for their exact scope. Owner-wide revocation and password change have separate permits/orderings in ADRs [0017](../../architecture/decisions/ADR-0017-owner-wide-session-revocation.md) and [0018](../../architecture/decisions/ADR-0018-account-password-change.md). Browser aborts and transaction timeouts are not hard deadlines for all server/native work.

## Configuration and deployment boundaries

Shipped application defaults are four shared password-work slots, 30 requests per client/selected route per 60-second window, and 10000 client/route windows. The corresponding application settings are `keynest.password-hashing.max-concurrent` and `keynest.rate-limit.limit`, `window-seconds`, `max-entries`. Environment bindings are `KEYNEST_PASSWORD_HASHING_MAX_CONCURRENT`, `KEYNEST_RATE_LIMIT_LIMIT`, `KEYNEST_RATE_LIMIT_WINDOW_SECONDS`, `KEYNEST_RATE_LIMIT_MAX_ENTRIES`. The four independent login settings and validated ranges are listed in [account throttling](login-throttling.md#configuration-and-bounds).

Both Compose files explicitly forward the password-work and four login settings. The hosted file also forwards `KEYNEST_RATE_LIMIT_TRUSTED_PROXIES`; the local file does not. Arbitrary host environment variables are not automatically passed into containers: inspect the actual Compose environment when applying other overrides. Keep client limiting enabled. Disabling it does not disable identifier admission or the shared hashing budget, and does reopen client-level abuse paths.

Every process has independent counters, windows and slots. Restarts discard limiter state; adding replicas increases aggregate admitted work/attempts. Sticky routing does not turn these controls into a shared budget. No Redis, shared account limiter or distributed admission service is implemented by this slice.

Before exposing an installation:

1. Restrict direct API reachability to the intended ingress. Trust only known direct proxy addresses/CIDRs, strip or replace untrusted forwarding headers at that ingress, and verify the resolved-client behavior through the actual chain. A shared proxy seen as one client can throttle unrelated users; overbroad trust can let attackers manufacture identities and fill the table. See [proxy identity guidance](../../operators/web-deployment.md#reverse-proxies-and-rate-limit-identity).
2. Configure ingress body-size, header/body-read, idle, upstream and total-request deadlines for the actual upload/workflows. Body-size bounds do not stop slow reads, and increasing proxy timeouts does not add server cancellation. Preserve the application's error, cache-control and `Retry-After` headers. Verify ordinary and rejected requests through the deployed ingress.
3. Apply shared edge admission and connection/traffic limits appropriate to the topology, including a deliberate account-abuse policy for replicas. Avoid reflecting account existence or recording raw identifiers/credentials in edge diagnostics. These deployment controls complement the local budgets; no particular cloud service is required.
4. Tune against disposable, representative workload measurements within CPU, native/heap memory, database and connection budgets. More slots consume more concurrent hashing resources; larger tables consume more memory; longer windows/cooldowns can prolong denial. Raising limits or restarting during an incident can amplify work/reset guessing budgets. This repository supplies no production throughput or DoS-immunity claim.

For a 429, respect `Retry-After` and reassess after expiry; repeated requests are not a bypass. For password-work 503, allow current work to finish and reassess capacity; there is no slot-specific retry timer. Do not automatically replay an uncertain export/restore/account mutation: use the endpoint's documented refresh/sign-in/review recovery instead. Rate/slot rejection and liveness/readiness are different signals. The [health probes](../../operators/runtime.md) do not expose slot/table saturation and can remain UP while a protected operation is refused. Collect only bounded, payload-free outcome evidence; this document adds no identifier, password, hash, token, body or key telemetry.
